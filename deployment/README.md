# Backend and reviewer deployment

This directory contains the shared deployment boundary for the CarePath backend and reviewer-facing Expo Web client.

## Local Docker Compose

Prerequisites: Docker Engine with Docker Compose v2.

```bash
cp deployment/.env.compose.example deployment/.env.compose
# Replace CAREPATH_POSTGRES_PASSWORD with a local-only password.
docker compose --env-file deployment/.env.compose up --build --wait
```

The stack contains:

- `api`: the FastAPI backend built from the repository `Dockerfile`; the production image also contains the Expo Web reviewer build;
- `db`: PostgreSQL 16 with a named data volume;
- `evidence_index`: a named volume mounted at `/app/data/guidelines/qdrant` for the existing Qdrant Local index architecture.

The API container waits for PostgreSQL to become healthy, runs `alembic upgrade head`, and then starts Uvicorn. No database port is published to the host. The API is exposed on `CAREPATH_API_PORT`, default `8000`.

The Docker image builds the Expo Web application in a separate Node build stage with `EXPO_PUBLIC_CAREPATH_API_URL=__CAREPATH_SAME_ORIGIN__`. FastAPI then serves the exported reviewer document and its static assets from the same origin as the API. This keeps the reviewer journey same-origin and avoids a second deployment or browser CORS dependency.

Verify the stack:

```bash
curl --fail -H 'Accept: text/html' http://127.0.0.1:8000/ >/dev/null
curl --fail http://127.0.0.1:8000/health/live
curl --fail http://127.0.0.1:8000/health/ready
curl --fail http://127.0.0.1:8000/openapi.json >/dev/null
```

Open `http://127.0.0.1:8000/` in a browser to run the reviewer-facing client against the same containerized backend.

Stop and remove containers:

```bash
docker compose --env-file deployment/.env.compose down
```

Add `-v` only when you intentionally want to delete the PostgreSQL and evidence-index volumes.

## Health checks

Three endpoints exist for distinct purposes:

- `GET /health/live`: process liveness only. It does not check external dependencies.
- `GET /health/ready`: deployment readiness. It returns HTTP 200 only when both the configured SQL database and active LLM provider are healthy. Dependency failures are reduced to `error`; exception text and credentials are never returned.
- `GET /health`: the original provider health endpoint, retained for backwards compatibility and used by the mobile journey connection indicator.

Container orchestrators and cloud platforms should use `/health/ready`. The Docker image itself uses `/health/live` so a temporary dependency outage does not cause a restart loop.

The external guideline index is intentionally not a readiness dependency. The core project currently uses Qdrant Local, and the generated index is not committed. Deployments that need external-evidence search must build or restore the configured `CAREPATH_EVIDENCE_INDEX_PATH` separately before that route is used.

## Environment variables

Application configuration uses the `CAREPATH_` prefix. The main examples are in the repository `.env.example`.

Deployment-specific variables:

| Variable | Purpose | Local Compose default |
| --- | --- | --- |
| `CAREPATH_DATABASE_URL` | SQLite or PostgreSQL SQLAlchemy URL | generated by Compose from the PostgreSQL service |
| `CAREPATH_EVIDENCE_INDEX_PATH` | Qdrant Local persistence directory | `/app/data/guidelines/qdrant` |
| `CAREPATH_REVIEWER_WEB_DIR` | optional directory containing an exported Expo Web `index.html` and assets | `/app/reviewer_web` in the production image |
| `CAREPATH_ENVIRONMENT` | `development`, `test`, or `production` | `development` |
| `CAREPATH_PRIVACY_MODE` | standard demo or strict local inference boundary | `standard_demo` |
| `CAREPATH_LLM_PROVIDER` | registered provider name | `mock` |
| `CAREPATH_LOG_LEVEL` | application log level | `INFO` |
| `CAREPATH_API_PORT` | host port used only by Compose | `8000` |
| `CAREPATH_POSTGRES_DB` | local Compose database name | `carepath` |
| `CAREPATH_POSTGRES_USER` | local Compose database user | `carepath` |
| `CAREPATH_POSTGRES_PASSWORD` | local Compose database password | required |

Do not commit real database passwords, API keys, tokens, or platform credentials. `deployment/.env.compose` is ignored by the repository-wide `.env.*` rule.

## Cloud deployment blueprint

`render.yaml` defines a Docker-based web service and a managed PostgreSQL database. Both resources explicitly use Render's `free` instance type so a new Blueprint does not silently select a paid default. The backend uses the same `Dockerfile`, migration entrypoint, and `/health/ready` probe as local Compose. Render injects the managed database connection string into `CAREPATH_DATABASE_URL`; no database secret is stored in the repository.

Because the production Docker image now contains the Expo Web export, the existing `carepath-api` service is also the reviewer-facing Web deployment. The public backend origin recorded in `deployment/public_backend_url.txt` is therefore the single reviewer URL: opening `/` shows the client, while `/docs`, `/openapi.json` and the API routes remain available on the same host.

The free configuration is intended only for reviewer/demo use. Render's current free-tier documentation states that free web services can spin down when idle and that free Render Postgres databases expire 30 days after creation. Before confirming a Blueprint deployment, always review the Render dashboard and verify that both `carepath-api` and `carepath-db` are shown as Free / $0. Do not deploy if the dashboard shows a paid instance type.

After deployment, verify the public API origin with:

```bash
python deployment/verify_backend.py https://YOUR-BACKEND-HOST
```

The verifier requires all of the following:

1. `/health/live` returns `status=ok`;
2. `/health/ready` returns `status=ready`;
3. `/openapi.json` is reachable and includes API metadata.

CP-020 additionally requires `/` to return the Expo Web client and the recorded primary browser journey to complete against the public backend. `.github/workflows/cp020-reviewer-client.yml` performs both the integrated Docker journey on pull requests and the public Render journey after the relevant change reaches `main`.

## Reviewer primary scenario

The primary reviewer flow uses synthetic data and requires no API console:

1. open the deployment root and confirm the API connection is connected;
2. select the built-in remote-worker persona and choose **Load demo**;
3. inspect the Today and Health Data summaries;
4. ask the prepared Coach question and inspect the structured evidence-backed answer;
5. open Plan & History, choose a lighter alternative for the first action and save feedback;
6. return to Coach and confirm the follow-up plan reflects the lighter action.

Each browser load generates fresh synthetic identifiers, so separate reviewer sessions do not intentionally share a user record.

## Fallback local demo

If the cloud reviewer deployment is unavailable, there are two supported fallback paths.

For the closest production-equivalent run, start the Docker stack and open the integrated client:

```bash
cp deployment/.env.compose.example deployment/.env.compose
docker compose --env-file deployment/.env.compose up --build --wait
# Open http://127.0.0.1:8000/
```

For a frontend-only fallback with no backend dependency:

```bash
npm --prefix apps/mobile ci
EXPO_PUBLIC_CAREPATH_MOCK_MODE=true npm --prefix apps/mobile run web
```

The frontend mock path remains synthetic and preserves the screen contracts needed to demonstrate navigation, trends, coaching structure, evidence, plan and feedback. It is a fallback only; CP-020 acceptance is based on the real deployed backend journey.

## CI validation

`.github/workflows/cp019-deployment.yml` builds the production image, starts the full Compose stack with PostgreSQL, waits for health checks, verifies migrations and HTTP endpoints, and tears the stack down on every pull request and on `main`.

`.github/workflows/cp020-reviewer-client.yml` verifies the integrated Expo Web root and executes the recorded browser journey against the containerized backend. On the relevant `main` push it waits for Render to publish that same image, rechecks public backend readiness, and executes the same primary journey against the real public origin.
